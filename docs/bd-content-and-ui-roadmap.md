更新日期：2026-09-12

### 1.2 当前模型表达能力不足

现有 `BuildVariantProfile` 只能表达通用词缀策略、移动鞋开关、一个传奇宝石替换和最后一个魔方威能替换。它不能可靠表达：

- 某个装备槽替换成什么，以及替换条件和代价。
- 技能、符文、被动、卡奈魔方、传奇宝石和普通宝石的成组变化。
- 大秘境冲层、大秘境速刷、T16 小秘境、悬赏、蓝门、梦魇回响和外观收集等真实用途。
- 低巅峰成型期、800 点前后、2000+ 高巅峰以及装备词缀洗掉主属性后的不同加点策略。
- 某项必须固定、条件可换或自由选择，以及替换后会破坏哪些联动。
- “此场景确实无需变化”的可审计原因。

### 1.3 装备视觉存在多个实现

当前至少有两套装备图标实现：BD 纸娃娃直接渲染图片和槽位背景，物品库使用 `BlizzardItemIcon`。BD 装备详情又维护了独立的 `detail-item-icon`。这会导致尺寸、品质底纹、边框、裁切和镶孔位置继续分叉。

目标是收敛为一个底层 `DiabloItemFrame`，所有页面只传物品数据、形状、尺寸和交互状态。

### 1.4 字号基线过小

`app/globals.css` 中仍有大量 6–9px 的正文、说明和列表文字。后续不应逐个选择器临时放大，而应先建立全站文字 token，再按语义替换。

## 2. 实施原则

1. 每个 BD 单独确认适用内容，不强迫所有 BD 都拥有同一组场景。
2. 每个适用场景都保存真实配置；不适用时明确记录原因，不伪造差异。
3. 页面差异摘要由配置 diff 计算，不由人工文案假装发生了变化。
4. 工厂只补结构性默认值，不自动替换装备、宝石、技能或魔方威能。
5. 每项替换必须有触发条件、收益、代价和互斥关系。
6. 巅峰建议必须区分 800 点前固定分类加点和 800 点后主属性/体能分配。
7. 每套 BD 保存资料版本、平台、来源和校对日期；来源冲突时保留判断说明。
8. 基础组件完成后再批量填内容；每套 BD 仍独立提交、独立测试、独立验收。

## 4. 目标数据模型

下面是目标能力，不要求一次提交全部实现；类型应按阶段逐步落地。

### 4.1 场景不是固定四格

用真实内容类型替代模糊的 `push/speed` 二选一：

```ts
type BuildContent =
  | "greater-rift-push"
  | "greater-rift-speed"
  | "nephalem-rift"
  | "bounty"
  | "echoing-nightmare"
  | "cosmetic-farm";

type ParagonBand = "pre-800" | "low" | "high";

type BuildScenario = {
  id: string;
  content: BuildContent;
  paragonBand: ParagonBand;
  applicability: "supported" | "not-recommended" | "not-applicable";
  reason: string;
  configuration?: BuildConfiguration;
  sourceRefs: string[];
  reviewedAt?: string;
};
```

页面仍可提供易懂的“用途”和“巅峰”控件，但选项必须来自该 BD 的 `scenarios`，不能先生成笛卡尔积再假定都有意义。

### 4.2 配置必须是可比较的完整对象

```ts
type BuildConfiguration = {
  gear: EquippedItem[];
  skills: EquippedSkill[];
  passives: string[];
  powers: EquippedPower[];
  legendaryGems: EquippedGem[];
  normalGems: GemRule[];
  follower: FollowerConfiguration;
  statPriorities: StatPriority[];
  rotation: RotationStep[];
};
```

实现可以采用“基准配置 + 显式 patch”减少重复，但解析后必须得到完整对象。校验器比较解析结果，确认页面所写的每条变化真的发生。

### 4.3 固定项与可替换项

装备、技能、符文、被动、威能和宝石统一使用选择策略：

```ts
type ChoicePolicy = {
  status: "locked" | "conditional" | "flexible";
  reason: string;
  alternatives: Array<{
    id: string;
    when: string;
    gain: string;
    cost: string;
    incompatibleWith?: string[];
    scenarios?: string[];
  }>;
};
```

界面文案约定：

- `必须固定`：构筑发动机、套装件数、关键乘区或生存闭环，替换会让 BD 失效。
- `条件替换`：在特定层数、巅峰、坚韧、冷却、组怪效率或玩法中替换。
- `自由槽位`：不破坏核心联动，可按词缀质量或个人操作选择。

所有替换都必须回答“什么时候换、换成什么、得到什么、失去什么”。

### 4.4 巅峰加点指导

每个 BD 增加 `paragonGuide`，至少覆盖：

- 800 点前：核心、进攻、防御、辅助四类的逐项顺序。
- 移速规则：角色面板 25% 上限中，装备移速与巅峰移速如何配合。
- 资源上限：是否增加伤害、循环或防御；无收益时明确跳过。
- 800 点后：主属性与体能的分配原则，不使用一条固定比例套全部 BD。
- 低巅峰保命阈值：什么情况下先补体能，达到什么实战条件后转主属性。
- 高巅峰词缀联动：装备洗掉主属性后，巅峰如何补回；范围伤、冷却、攻速断点如何影响选择。
- 主机说明：Nintendo Switch 操作、锁定和拾取差异会影响的加点或配置。

```ts
type ParagonGuide = {
  pre800: Record<"core" | "offense" | "defense" | "utility", ParagonPriority[]>;
  post800: Array<{
    condition: string;
    mainStat: string;
    vitality: string;
    rationale: string;
  }>;
  checkpoints: Array<{
    label: string;
    target: string;
    adjustment: string;
  }>;
};
```

## 5. 页面设计计划

### 5.1 BD 场景切换

切换后页面顶部展示自动计算的“本配置发生了什么”：

- 装备：新增、移除、替换。
- 技能/符文/被动：替换项及原因。
- 魔方和宝石：替换项及适用内容。
- 词缀和巅峰：优先级或分配策略变化。
- 手法：新增、删除或调整的步骤。

如果两个场景配置一致，必须显示人工校对过的 `reason`，并且不能把该状态计为“有差异”。

### 5.2 固定与替换说明

纸娃娃和技能区使用简短状态标记；点击后在详情区展示完整替换条件。不要把全部说明堆在装备盘上。

详情区顺序：

1. 当前物品在 BD 中的职责。
2. 固定程度及原因。
3. 可替换方案、触发条件、收益与代价。
4. 当前场景为什么选它。
5. 词缀、镶嵌、获取和避坑。

### 5.3 统一装备框

新增底层 `DiabloItemFrame`，由它统一处理：

- 普通/制作、传奇、套装的品质底纹和边框。
- 方形、普通竖框、胸甲大竖框等官方比例。
- 原图居中裁切，不拉伸成正方形。
- 镶孔宝石、悬停、选中、关联高亮和禁用状态。
- `sm`、`md`、`lg` 三档尺寸；比例由物品分类决定。

复用位置：

- BD 角色纸娃娃装备槽。
- BD 装备详情左侧。
- 随从纸娃娃装备槽。
- 物品 Tab 列表左侧。
- 物品详情左侧。

物品详情移除大幅氛围背景图，左侧只保留装备框；右侧继续显示结构化物品信息。

### 5.4 随从纸娃娃

视觉基线采用用户截图和[暴雪角色页](https://us.diablo3.blizzard.com/zh-tw/profile/DyS-1311/hero/159448381)的布局关系，不复制网页代码：

- 桌面端三名随从并排，每栏独立标题、人物半身/全身和装备盘。
- 人物在上半区偏右，装备槽围绕人物分布；武器和副手位于底部两侧。
- 未装备槽保留暗色轮廓，已装备槽使用统一装备框。
- 技能位于装备盘下方，保持 2×2 排列；说明和推荐原因放在技能区之后。
- 推荐随从只通过标题、边框和状态文字强调，不改变槽位几何。
- 移动端改为单栏逐名展示，不把三栏压缩到不可读尺寸。

第一阶段继续使用项目已有的本地随从人物素材；若素材比例不足，再单独补资源，不把人物照片裁成装备背景。

### 5.5 全站字号与行高

先在 `:root` 建立语义 token，再替换散落字号：

```css
--text-caption-size: 12px;
--text-caption-line: 1.5;
--text-meta-size: 13px;
--text-meta-line: 1.55;
--text-small-size: 14px;
--text-small-line: 1.65;
--text-body-size: 16px;
--text-body-line: 1.75;
--text-heading-sm-size: 18px;
--text-heading-sm-line: 1.4;
```

执行规则：

- 正文、装备用途、替换条件和攻略说明不低于 14px。
- 12px 仅用于槽位标签、次要元信息和装饰性题注。
- 6–9px 不再用于需要阅读的内容。
- 字号不按视口宽度连续缩放；窄屏通过换行、布局重排和容器宽度解决。
- 每一阶段都检查按钮、标签、装备框和三栏随从区是否因字号增加发生遮挡。

## 8. 单套 BD 的完成定义

一套 BD 只有同时满足以下条件才能标记 `fully-reviewed`：

- 适用场景和不适用场景均已说明。
- 每个适用场景能解析出完整且合法的配置。
- 所有场景之间的差异由程序计算，文案与 diff 一致。
- 800 点前、低巅峰、高巅峰加点完整。
- 所有装备、技能、符文、被动、威能和宝石都有固定程度。
- 所有条件替换都有触发条件、收益、代价和互斥关系。
- 因果链和输出手法引用当前场景实际存在的项目。
- 来源、赛季、平台和校对日期完整。
- 数据校验、路由测试和关键交互测试通过。
- 人工检查至少覆盖桌面和手机两个视口。

在这些条件完成前，页面可以展示“已校对部分”，但不能再用一个宽松字段把整套 BD 标记为完整。
