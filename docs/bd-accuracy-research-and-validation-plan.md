# BD 内容准确性审计、资料源评估与验证计划

## 执行摘要

这次审计的结论不是“少量细节需要润色”，而是：**整改前的 51 套 BD 只能证明通过了结构校验，不能证明已完成内容校对；其中至少 23 套是由同一个通用工厂批量生成的伪完整配置，已经发现会让构筑失效或直接误导新手的确定性错误。** 因此不应继续对外展示“51 套完整校对”。

用户提出的三个判断，评估如下：

| 判断 | 结论 | 需要校正的部分 |
| --- | --- | --- |
| 高巅峰大量统一换钻石、装备不变，可能是批量偷懒 | **基本准确，而且问题比表象更严重** | “装备不变”本身不一定错；真正的问题是没有逐套证据、所有职业套用同一巅峰/宝石模板，并且模板与部分来源明确冲突 |
| 每套 BD 固定四种模式不合理 | **准确** | “冲层/速刷”仍可作为一级用途分类，但不能把低/高巅峰与用途做固定笛卡尔积，更不能把大秘境速刷、T16、悬赏、敌意幻象塞进同一个“速刷”配置 |
| Maxroll 可能比 Icy Veins 更好 | **方向上值得引入，但不能简单替换** | 两者都不是权威事实源，也都可能有陈旧页面；推荐“官方规则 + Icy/Maxroll 双源 + 天梯/实战证据 + Switch 终验”，而不是选一个站作为唯一答案 |

优先级建议：先止损，再重构数据模型，然后逐套复核。立即止损至少包括：把 23 套工厂生成 BD 降为 `draft` 或 `unverified`、修复 4 套 LoD 缺少梦之遗礼宝石和梦遗轰击武器宝石错误、移除不具备证据的全场景 `supported`、停止用“51/51 valid”代表内容准确。

## 1. 审计范围、基线与置信度

本报告以仓库当前数据、Nintendo Switch、简体中文、单人玩法、第 39 赛季为基线。项目配置声明为 S39 / 2.7.8 / NS / 四魔方槽；暴雪官方页面确认第 39 赛季于 2026 年 6 月 26 日开始，赛季主题包含暗影分身和可使用前三类威能、但不能与已有威能叠加的第 4 魔方槽。[^1]

研究分为四层：

1. **代码审计**：检查生成器、运行时选择逻辑、校验器、审计报告和文档状态。
2. **数据审计**：解析 51 套 BD 的 204 个场景，统计用途、适用性、差异、来源域名和通用模板指纹。
3. **外部资料抽查**：使用官方赛季页、官方天梯、Icy Veins 当前 S39 页面、Maxroll 当前维护信号、主机专项资料进行交叉核验。
4. **机制反例验证**：选择能一票否决通用规则的构筑，例如 LoD、荆棘、智力职业普通宝石和仅冲层 BD。

置信度定义：

- **确定**：代码直接生成或官方/构筑专页明确说明，能稳定复现。
- **高**：两个独立来源一致，或资料与游戏机制能相互印证。
- **中**：当前指南或社区资料支持，但尚未在 Nintendo Switch 实机复验。
- **待验证**：仅有单一二手来源、旧资料或推断。

本次没有逐套在 Switch 中完整装配并跑图，因此不会把未抽查的 28 套称为“准确”；报告只证明当前“51 套全部准确”的说法不成立，并给出可执行的全量验证方法。

| 大秘境冲层场景 | 98 | 49 套各有低/高两份 |

上述统计可由当前 `configurationBase + scenarios` 解析结果复现。它同时解释了用户观察到的现象：大量 BD 的“高巅峰”只是五颗防具宝石统一改成钻石并改两行词缀优先级，而配装没有经过构筑专属判断。

### 2.2 23 套“完整评审”来自通用生成器

整改前，`app/data/class-build-factory.ts` 中的 `createGenericReviewedGuide()` 做了以下事情：

- 按数组顺序取前 13 件装备、前 6 个技能、前 4 个被动和前 4 个威能。
- 给所有构筑固定三颗传奇宝石：困者、勾玉、受罚者。
- 给所有构筑固定武器绿宝石。
- 给所有职业的 800 巅峰前核心属性写“力量”。
- 创建同样的四场景，并把高巅峰防具统一改成 5 颗钻石。
- 给四场景全部标记 `supported`，只引用一个 URL。
- 最后直接写入 `reviewStatus: "fully-reviewed"` 和 `variantCompleteness: "complete"`。

这不是“人工校对后发现配置恰好相同”，而是程序先生成同样的答案，再把答案标为完成。命中该指纹的 23 套如下：

| 职业 | BD |
| --- | --- |
| 野蛮人 | 大地跃击、九十蛮狂乱、不朽冲锋 |
| 圣教军 | 圣光锤丁、梦遗轰击 |
| 猎魔人 | 掠夺集束塔、不洁多重射击、娜塔亚尖刺陷阱、暗影三刀、梦遗连射 |
| 武僧 | 尹娜幻身、正义风雷冲、猴王风雷冲、猴王敲钟、梦遗敲钟、乌莲娜爆裂掌、千飓疾风击 |
| 巫医 | 亚拉基尔蜘蛛、亚拉基尔愤怒鸡、祖尼玛毒镖、玉魂收割、魔牙巨尸、梦遗魂弹 |

另有 7 套魔法师没有命中上述指纹，但同样由 `completeWizardGuide()` 批量填充固定四场景、通用巅峰和通用速刷规则。它们比 23 套通用工厂数据更细，但仍然不能据此认定为逐套完成；尤其是每套都把 T16、蓝门、低层大秘境或悬赏合并，并全部标记 `supported`。

### 2.3 已确认的 P0 错误

#### 2.3.1 四套 LoD 构筑没有装备梦之遗礼

`lod-bombardment`、`lod-rapid-fire`、`lod-wol`、`lod-barrage` 的通用基础配置都是困者 + 勾玉 + 受罚者，没有梦之遗礼。对于以 LoD 为构筑发动机、又没有梦魇对戒的配装，这会直接丢失整套散件乘区，属于构筑失效，不是微小词缀争议。Icy Veins 的 LoD 连射说明也明确把梦之遗礼作为构筑基础。[^2]

#### 2.3.2 梦遗轰击错误使用武器绿宝石

同一通用工厂给 `lod-bombardment` 配了武器绿宝石。荆棘伤害不能暴击，因此暴击伤害宝石不产生该模板预期的收益；当前资料明确建议荆棘轰击武器使用黄宝石，并把黄宝石称为荆棘构筑的必需武器宝石。[^3] 这也是一个足以证明“通用宝石模板不可用于内容校对”的反例。

#### 2.3.3 23 套全部写“力量”巅峰

通用生成器在 `pre800.core` 中硬编码“力量”，因此猎魔人、武僧、巫医也会得到错误主属性。即使页面的其他层可能显示职业化词条，这个数据源仍已失去内容可信度。

#### 2.3.4 高巅峰统一钻石与引用来源直接冲突

以祖尼玛毒镖为例，项目高巅峰把胸甲和裤子统一改成钻石；其引用的 Icy Veins S39 装备页却建议智力职业初期用黄宝石，在冲层时根据坚韧瓶颈改红宝石来补护甲，并明确说明没有固定巅峰断点。该页还给出正确的职业主属性、巅峰顺序和专属传奇宝石：简易之力、侍从宝石以及受罚者/困者条件选择。[^4] 项目同时错在颜色、切换条件和传奇宝石。

通用宝石指南也指出：智力职业通过智力获得抗性，后期常缺的是护甲；钻石更常用于力量/敏捷职业补全抗。[^5] 因此“2000+ 全职业统一钻石”不是合理简化。

#### 2.3.5 所有构筑都被判定适用四场景

Icy Veins 当前 S39 门户会给构筑分别标注 `gr-pushing`、`speed-gr`、`speed-nr`、`bounties` 等用途，并单独维护 Solo Push、Solo Speed GR、Solo Speed T16 排名。该门户把九十蛮狂乱、恐惧冰吞、梦遗连射、梦遗敲钟等页面只列为单人冲层，而不是自动提供全部速刷变体。[^6] 这不意味着这些构筑“绝对不能打 T16”，而是说明当前项目没有证据把它们的四格全部标成推荐配置。

#### 2.3.6 来源字段无法支撑“已评审”

整改前的 `sourceRefs` 只是字符串数组，没有标题、作者、更新时间、赛季、平台、用途或它支持的具体结论。魔法师批量来源还把一段内部说明文本塞进 `sourceRefs`；页面会把每个字符串都渲染为 `<a href={source}>`，导致非 URL 文本成为错误链接。引用 Maxroll 时，魔法师七套只引用分类首页，而不是精确构筑/变体页。本轮已经阻止非 URL 被渲染为链接并移除这两类伪来源，但逐套迁移到结构化来源仍未完成。

### 2.4 为什么现有校验器会全部通过

整改前的 `validateReviewedBuildGuide()` 主要验证：场景 ID 是否重复、默认场景是否存在、装备/技能/被动/威能 ID 是否存在、配置是否重复、非默认场景无差异时是否有说明，以及 `fully-reviewed` 是否存在巅峰和至少一条选择策略。

它没有验证：

- 来源是否为有效 URL、是否指向当前构筑的精确变体。
- 来源的赛季、补丁、平台、更新时间和作者。
- 某个来源具体支持哪个装备、宝石、技能、词缀或场景结论。
- LoD 是否携带梦之遗礼、荆棘是否错误追求暴击、主属性是否匹配职业。
- 一个 BD 是否真的适合某个用途，或 T16、GR 速刷、悬赏、敌意幻象是否被错误合并。
- Nintendo Switch 与 PC 的机制差异。
- “高/低巅峰”的切换是否有实际阈值证据。

因此，当前 `51 valid` 应更名为“51 套结构可解析”，不能作为准确率指标。审计脚本甚至把 `total === fullyReviewed === valid === 51` 写成成功条件，形成了状态字段自证状态字段的闭环。

### 2.5 文档状态也发生漂移

`docs/bd-content-and-ui-roadmap.md` 同一文件顶部写“51 套完整、0 套剩余”，正文又写“26 套完整、25 套待校对”；后文再把 51 套全部勾选。`docs/technical-debt.md` 仍写“1 套完整、2 套部分、48 套待校对”，`docs/project-goal-and-gap.md` 则写“51 套仍未全部逐套校对”。这种矛盾会让下一位维护者优先相信最新且最乐观的状态，从而继续在错误基线上迭代。

## 3. 对“装备不变”和“巅峰两档”的准确判断

用户观察到“高巅峰只是换钻石，装备基本不变”，其中要分开看：

- **装备不变可以是正确结果。** 巅峰提高后，构筑的核心发动机、套装和关键乘区通常不会因为跨过某个整数巅峰就改变。常见变化可能只是把装备主属性洗成范围伤/冷却/攻速、调整体能、换普通宝石，或在守护者与奥吉德之间按实际面板换装。
- **固定 2000 阈值通常不够严谨。** Icy Veins 的祖尼玛毒镖等页面明确使用“当坚韧开始限制推进时切换”的条件，而不是统一的 P2000。真实断点还受远古件数、卡德山、宝石等级、目标层数、操作熟练度和平台影响。
- **不应为了让按钮有变化而强行换装备。** 如果证据表明高低巅峰完全共用配装，应只展示一套配置，再给条件化的词缀/宝石建议；不能制造一个假的完整场景。
- **低巅峰仍有产品价值，但更适合做成长指导。** 对新手，`刚满 70 → 套装成型 → 800 前 → 装备/卡德山成型 → 极限冲层` 比 `<2000 / 2000+` 更可执行。只有在某套 BD 存在可解释、可验证的守护者/奥吉德或其他阈值时，才显示专属断点。

结论：保留“成长阶段”概念，取消它作为每个用途都必须复制一份完整配装的固定轴。

## 4. 固定四模式为什么不适合这个产品

整改前的 UI 只查找 `${mode}-${paragon}`，并永久渲染“冲层/速刷”和“低/高巅峰”两个二选一控件。这个模型会制造三个问题：

1. **用途混淆**：通用工厂的 `speed-low` 是大秘境速刷，`speed-high` 却变成小秘境。用户只切了巅峰，实际玩法类型也悄悄改变。
2. **错误推荐**：站桩冲层或低效率构筑也被展示为“支持 T16/速刷”，却没有不推荐原因。
3. **真实变体被压扁**：T16 小秘境、GR 速刷、悬赏、敌意幻象、梦魇回响、地精/外观的掉落规则、首领压力、路线和金币机制不同，往往需要不同装备。

建议把“用途”改成按 BD 数据动态出现的首要入口：

```ts
type Activity =
  | "greater-rift-push"
  | "greater-rift-speed"
  | "nephalem-rift-t16"
  | "visions-of-enmity"
  | "bounty"
  | "echoing-nightmare"
  | "goblin-or-cosmetic-farm";

type Applicability = "recommended" | "viable" | "not-recommended" | "not-applicable";
```

每个 BD 只创建有证据的活动场景。没有专属速刷变体时可以：

- 不显示该按钮；或
- 显示“能打但不推荐”，并跳转到同职业更合适的速刷 BD；或
- 明确复用另一场景的配置和原因，而不是伪造 diff。

成长阶段放到场景内部，作为条件化建议：

```ts
type ProgressionAdvice = {
  condition: string;       // 例如“守护者收益仍高于奥吉德”
  observable: string;      // 玩家在面板或实战里怎么判断
  change: BuildPatch;
  gain: string;
  cost: string;
  evidenceRefs: string[];
};
```

页面应先问“你要做什么”，再展示该用途下的可用配置。若只有词缀或宝石条件变化，就在同一页面内展示“坚韧不足时 / 伤害不足时”的建议，不再额外制造一套“高巅峰 BD”。

## 5. Icy Veins 与 Maxroll：谁更适合做来源

### 5.1 结论

**Maxroll 值得加入，而且在变体组织、D3Planner 和可比较配装方面通常更适合作为结构化参考；但它不应取代 Icy Veins，更不能成为 Nintendo Switch 项目的唯一来源。** Icy Veins 当前 S39 页面更新活跃、可抓取、变体页和装备/技能/巅峰拆分清楚；Maxroll 在 2026 年 6 月仍发布 S39 排名和指南更新，但本次自动研究无法读取其正文，因为站点拒绝机器抓取，只能从当前作者视频、搜索索引和项目已有精确链接确认其仍在维护。[^7]

| 维度 | Icy Veins | Maxroll | 本项目怎么用 |
| --- | --- | --- | --- |
| S39 更新信号 | 强；大量页面有 2026-06 更新日期和 changelog | 强；S39 排名/升级内容仍在更新 | 两者都检查更新时间，不看品牌名直接放行 |
| 变体拆分 | 强；主构筑、GR 速刷、NR 等常为独立页 | 通常强；指南与 Planner 便于比较 | 必须引用精确变体 URL，不引用分类首页 |
| 词缀/技能解释 | 详细、可读性好 | Planner 和表格通常更直观 | Icy 适合解释“为什么”，Maxroll 适合核对“具体是什么” |
| 自动采集 | 当前可读取 | robots 限制明显 | Maxroll 需要人工浏览后保存审计摘录，不能假装已自动验证 |
| 陈旧风险 | 存在；当前玛拉uder 多重页面同时出现 2.7.9、S39 和残留 S33 文案[^8] | 同样存在；社区有 2026 年 T16 配置陈旧的具体反馈[^9] | 每条结论做页内一致性检查，并用第二来源或实机化解冲突 |
| 主机适配 | 主要按 PC 思路 | 同样明显偏 PC | 都只能作为起点，Switch 专项机制必须独立验证 |

### 5.2 推荐来源层级

1. **暴雪官方赛季/补丁/游戏内文本**：确认赛季主题、魔方槽、物品/技能规则。官方不会替你决定最佳完整配装。
2. **Icy Veins + Maxroll 精确构筑变体**：至少两源核对核心装备、技能、宝石、威能、词缀和用途；不得用站点分类页充数。
3. **官方当季天梯**：验证冲层构筑确实有现实使用和层数表现；暴雪 S39 天梯可查看当前职业排名和完成时间。[^10] 天梯证明“有人成功”，不自动证明“适合新手”或“适合 Switch”。
4. **可信作者视频/Planner/社区共识**：用于解释操作、断点和新鲜变体；记录作者、发布日期、平台、巅峰和目标内容。
5. **Nintendo Switch 实机**：最终裁决手柄操作、自动瞄准、技能施放、性能和主机独有机制。

### 5.3 Switch 不能只照抄 PC

项目明确以 NS 为基线，但绝大多数外部构筑站默认服务 PC。主机专项资料指出，能量气旋在主机上可在引导时施放且不会中断引导，并可在墙角叠加；由此产生主机特有的火鸟气旋玩法。[^11] 当前项目却收录 PC 向“火鸟爆炸冲击”，没有明确的火鸟气旋主机构筑。这不证明现有火鸟条目一定不可玩，但说明“NS 基线”目前没有落实到选品和验证流程。

每套 BD 必须增加 `platformStatus`：

- `switch-verified`：已在 Switch 实机验证。
- `console-sourced`：有当前主机专门资料，尚未本项目实测。
- `pc-derived`：来自 PC 配装，仅完成机制差异检查。
- `platform-risk`：已知瞄准、施法、帧率或机制可能影响配置。

## 6. 目标数据与证据模型

### 6.1 内容状态不能再由结构字段替代

建议采用逐级状态：

```ts
type EvidenceStatus =
  | "unverified"
  | "source-checked"
  | "cross-checked"
  | "switch-tested"
  | "published";
```

含义：

- `unverified`：可展示为待复核内容，但不得称推荐。
- `source-checked`：精确主来源已核对。
- `cross-checked`：第二来源、机制与来源冲突已处理。
- `switch-tested`：完成该场景的 NS 实机功能验证。
- `published`：内容、自动化、人工复核和 UI 均通过发布门槛。

`variantCompleteness` 只描述结构，不再参与内容准确率统计。

### 6.2 来源必须结构化到“结论级”

```ts
type SourceRecord = {
  id: string;
  url: string;
  title: string;
  publisher: "blizzard" | "icy-veins" | "maxroll" | "community" | "internal-test";
  author?: string;
  publishedAt?: string;
  updatedAt?: string;
  accessedAt: string;
  season?: number;
  patch?: string;
  platform: "pc" | "console" | "switch" | "all" | "unknown";
  activity?: Activity;
  archivedSnapshot?: string;
};

type EvidenceClaim = {
  path: string;            // gear.weapon、gems.weapon、skills[2] 等
  claim: string;
  sourceIds: string[];
  status: "confirmed" | "conflict" | "inferred" | "in-game-verified";
  rationale?: string;
};
```

这样才能回答“这颗宝石是谁推荐的、针对哪个玩法、哪一赛季、PC 还是 Switch、什么时候看过”。来源冲突保留为显式数据，不在代码里悄悄选一个。

### 6.3 配置复用要显式，不要复制假场景

如果 GR 速刷与 T16 的装备完全相同，可以使用 `configurationId` 或 `sameAsScenarioId` 复用，并写明经过核对后的原因。页面显示“共用配置”，而不是展示两个内容相同、都声称独立校对的 patch。

如果资料只支持冲层，则不创建速刷配置；如需帮助新手，展示同职业替代建议，例如“本 BD 能过 T16，但效率低，推荐切换到不洁多重/恐惧冰吞”。

## 7. 单套 BD 的研究与验证 SOP

下面流程必须逐套执行。一次只把一套 BD 提升到更高状态，禁止通过工厂一次把一批条目标为完成。

### 步骤 1：锁定身份和范围

记录：`buildId`、职业、中文/英文名称、核心技能、套装或 LoD/LoN 发动机、目标平台、赛季、补丁、单人/组队范围。检查目录名与来源是不是同一构筑，例如“千飓疾风击”不能引用“千飓风雷冲”页面。

通过条件：核心伤害来源、核心防御闭环和至少三个不可替换项能用一句话解释。

### 步骤 2：建立“用途候选表”

分别调查：GR 冲层、GR 速刷、T16 小秘境、敌意幻象、悬赏、梦魇回响、地精/外观。对每项记录 `recommended / viable / not-recommended / not-applicable / unknown`，不得默认全部适用。

检索方法：

1. 在 Icy Veins 当前职业门户查看该构筑标签和独立变体链接。
2. 在 Maxroll 打开精确指南，逐个检查 Activities/Variants/Planner，不使用分类首页。
3. 搜索“构筑英文名 + Season 39 + Switch/console + activity”。
4. 冲层查看当季天梯和角色详情；速刷查看有完整装备、巅峰、地图和计时信息的视频或日志。

通过条件：每个公开显示的用途至少有一个精确来源；`recommended` 应有双源或实机证据。

### 步骤 3：抄录基准配置，不做推断填空

逐项抄录并核对：13 个装备槽、6 技能和符文、4 被动、3/4 魔方槽、3 传奇宝石、普通宝石、随从、药水、词缀顺序、操作循环。每个字段绑定 `EvidenceClaim`。

未知项保持 `unknown` 或阻止发布，不能用全局默认值补齐。构筑站出现内在矛盾时，截取冲突位置并进入步骤 6。

### 步骤 4：验证核心不变量

自动和人工同时检查：

- LoD：必须有梦之遗礼或明确的梦魇对戒方案；不得激活任何套装奖励。
- 荆棘：武器宝石、暴击词缀、范围伤等必须符合具体伤害机制；例外需要来源说明。
- 宠物：核对侍从宝石、攻速断点以及“角色攻速是否实际改变宠物攻击频率”。
- 引导：核对减耗、攻速、勾玉/太极、引导是否被技能打断。
- 元素循环：元素伤、技能符文、全能法戒窗口必须一致。
- 套装件数：皇家华戒生效前后实际档位正确。
- 职业主属性：野蛮人/圣教军力量，猎魔人/武僧敏捷，死灵/巫医/法师智力。

任何核心不变量失败，该场景直接回到 `draft`。

### 步骤 5：单独研究每个用途变体

比较基准与变体的真实差异：装备、技能/符文、被动、魔方、传奇/普通宝石、随从、词缀和手法。特别检查：

- GR 不掉金币，金织带/囤宝者/贪婪之戒链不能误入 GR。
- T16、悬赏和敌意幻象都可能掉金币，但地图长度、交互、首领和精英密度不同，不能因此自动共用。
- GR 速刷强调稳定 2–3 分钟或目标经验效率；T16 强调钥匙、移速和瞬时清屏；两者不能只用“速刷”概括。
- 梦魇回响有独立的范围、控制、塔和生存需求。

若两个用途确实共用，记录 `sameAsScenarioId` 和来源支持的原因。

### 步骤 6：处理来源冲突

冲突按以下顺序裁决：

1. 先排除赛季、补丁、用途和平台不一致。
2. 检查页面标题、正文、变体页和 changelog 是否互相矛盾。
3. 复核游戏内物品/技能文本与伤害机制。
4. 查看当前天梯或近期完整实战，而不是只看作者结论。
5. 在 Switch 建立 A/B 配置测试关键争议。
6. 仍无定论时保留两个方案，写明各自条件和风险，状态记为 `conflict`，不伪装唯一最优解。

### 步骤 7：把巅峰改成可观察条件

800 前的四类加点可以明确排序；800 后不要只写“2000+”。每条成长建议必须包含：触发条件、玩家如何观察、要改什么、得到什么、失去什么。

可接受示例：“当连续三次目标 GR 因被秒而失败，且技能减伤覆盖正常时，将胸裤主属性宝石改为补护甲方案；稳定后再测试伤害方案。”

不可接受示例：“高巅峰统一五钻石”“2000 后统一把主属性洗掉”。

### 步骤 8：Nintendo Switch 功能验证

为每个拟发布场景保留实机记录：

- 角色巅峰、宝石等级、远古/卡德山情况和面板截图。
- 装备、技能、符文、被动、魔方和随从全屏截图或短视频。
- 手柄瞄准、需要定点施法的技能、自动锁定、引导中施法是否符合资料。
- 核心 buff/debuff 是否能维持，金币链、套装档位和传奇宝石是否真正触发。
- 发生失败时记录死因、资源断档、冷却断档或首领单体不足。

功能门槛：连续 3 次完成目标活动且构筑发动机无失效。性能评价建议使用 5–10 次样本记录中位时间、最慢时间、死亡次数和地图异常；这只用于描述体验，不应把小样本包装成全局排行。

### 步骤 9：第二人复核与 UI 验收

复核者不看作者的预期答案，按来源从零检查：

- 页面每个槽位与证据记录一致。
- 选择用途不会暗中改变另一个维度。
- 不适用或不推荐场景不会展示为绿色“支持”。
- 共用配置清楚说明为何共用。
- 所有来源链接可点击、是精确页面、不是内部文字。
- 桌面和手机上核心联动、避坑和替代方案都可读。

通过后才进入 `published`。

## 8. 自动化验证计划

### 8.1 把结构校验和内容校验分开

保留现有 `validateReviewedBuildGuide()` 作为 `validateBuildSchema()`，另加：

- `validateBuildSemantics()`：职业、LoD、荆棘、套装、宝石、用途与机制不变量。
- `validateBuildEvidence()`：来源 URL、精确变体、更新时间、平台、声明覆盖率、冲突状态。
- `validateBuildPresentation()`：UI 可达性、按钮来自实际场景、标签与 `content` 一致。

审计报告同时输出：`schemaValid`、`semanticChecksPassed`、`evidenceCoverage`、`switchVerified`、`publishable`，禁止再用一个 `valid` 混合所有含义。

### 8.2 必须新增的硬规则

1. 非力量职业的巅峰核心属性出现“力量”时报错。
2. `lod-*` 没有梦之遗礼/LoN 或激活套装奖励时报错。
3. 荆棘构筑武器使用绿宝石时报错；暴击词缀标记为需解释。
4. 智力职业高巅峰防具全钻石至少报警，必须有精确来源与理由。
5. 场景来源必须是 HTTPS URL，分类首页不能满足 `cross-checked`。
6. `sourceRefs` 不允许纯文本；页面不得把非 URL 渲染成链接。
7. `content` 与标签一致；切换成长阶段不得改变 activity。
8. `supported/recommended` 必须有精确场景来源或实机证据。
9. S39 第四槽只能在 S39 覆盖层出现，并检查不与前三槽同威能叠加。
10. 工厂生成的固定指纹、同日同源批量“完成”和全场景 `supported` 触发审计失败。

### 8.3 证据覆盖率

按字段计算覆盖率，而不是按“有一个 URL”计数：

```text
核心配置覆盖率 = 有来源或实机证据的核心字段 / 全部核心字段
场景覆盖率 = 有精确用途证据的公开场景 / 全部公开场景
平台覆盖率 = 已完成 Switch 风险检查的场景 / 全部公开场景
```

建议发布门槛：核心配置 100%，场景 100%，平台风险检查 100%；非核心自由槽可以低于 100%，但必须显示为“自由选择”而非“最优”。

## 9. 实施阶段与验收门

### 阶段 0：立即止损（0.5–1 人日）

交付物：

- 将 23 套 `createGenericReviewedGuide()` 结果降为 `draft/unverified`。
- 将 7 套魔法师批量结果标为“需逐套证据复核”，而不是继续当作全部完成。
- 修复 4 套 LoD 缺梦之遗礼、梦遗轰击武器宝石、23 套巅峰力量等确定错误；无法立即修复时隐藏推荐配置。
- UI 只展示真实存在的场景；暂时不能重构时至少把无证据场景标为“未验证”。
- 统一路线图、交接手册、技术债和项目差距文档的真实状态。

验收门 G0：线上不再声称 51 套全部完成；已知会让 BD 失效的配置不再作为推荐展示。

### 阶段 1：数据和证据模型（2–4 人日）

交付物：

- Activity、Applicability、ProgressionAdvice、SourceRecord、EvidenceClaim、EvidenceStatus、PlatformStatus 类型。
- 动态场景 UI 和 `sameAsScenarioId/configurationId` 复用。
- 结构/语义/证据/展示四类校验与新版审计 JSON。
- 迁移脚本只迁结构，不自动提升内容状态。

验收门 G1：可以准确表达“只有冲层”“GR 速刷和 T16 不同”“配置共用但成长建议不同”“PC 来源、Switch 未验”。

### 阶段 2：5 套试点（3–6 人日）

建议试点覆盖不同机制：

1. `tragoul-nova`：保留人工样板，重做证据链和 Switch 验证。
2. `lod-bombardment`：LoD + 荆棘双重硬规则。
3. `zuni-darts`：宠物、攻速、智力职业宝石和条件化巅峰。
4. `h90-frenzy` 或 `lod-rapid-fire`：验证“只有冲层/不推荐速刷”的 UI。
5. `firebird-eb`：处理 PC 配装与主机火鸟气旋的分叉。

验收门 G2：五套均有结论级证据、来源冲突记录、动态用途、自动规则和至少一次 Switch 功能验收；流程耗时被记录，可据此估算全量工作。

### 阶段 3：新手优先批次（5–8 人日）

先校对 S39 海德格赠礼对应的 7 套：荒原、罗兰、不洁、千飓、拉斯玛、魔牙、塔拉夏。暴雪官方明确列出这七套赠礼，最符合“让新手更容易入门”的产品目标。[^1]

每套不仅提供终局清单，还要增加：刚拿两件/四件/六件时怎么过渡、第一件关键散件、血岩与黄装升级优先级、第一套能稳定刷哪个内容。

验收门 G3：新手通过本项目领取当季赠礼后，能从 70 级完整走到第一个可验证的 T16/GR 场景，不需要猜关键装备和机制。

### 阶段 4：全量 51 套（约 15–30 人日，按试点修正）

顺序建议：

1. 23 套通用工厂数据，先处理 LoD、荆棘、智力职业和来源错配。
2. 热门且覆盖明确用途的构筑，例如恐惧冰吞、正义风雷冲、勇气天拳、愤怒鸡等。
3. 28 套非通用指纹数据逐套复核；“不是通用工厂”不等于准确。
4. 冲层专用、低 tier、外观和路线型构筑最后处理，并清楚显示其定位。

每完成一套，独立数据提交、独立证据记录、独立测试，不以一批构筑共享同一套完成文案。

验收门 G4：51 套没有未知核心字段；所有公开场景都有精确来源；所有 NS 风险已标记；`published` 与审计结果一致。

### 阶段 5：赛季维护机制（持续）

- 赛季公布时先冻结上一季数据，创建新赛季覆盖层。
- 官方规则变化触发受影响字段列表，不全量复制旧 `fully-reviewed`。
- 每个来源保存 `updatedAt/accessedAt`，30–60 天或新赛季时检查失效链接和内容变化。
- 自动生成“待复核原因”：补丁变化、来源更新时间晚于本项目、页面标题/正文版本冲突、天梯构筑异常变化、Switch 风险未验证。

## 用途矩阵

## 11. 最终决策建议

1. **接受用户对“批量偷懒”的判断**，但用更准确的术语描述为“生成式占位数据被错误升级为已校对数据”。
2. **不要把‘装备没变’列为错误规则**；应检查是否有来源和条件。完全共用可能正确，虚构差异反而更坏。
3. **取消全站固定四格**；以真实 Activity 驱动场景，成长建议成为场景内条件，不再改变 Activity。
4. **引入 Maxroll，但不做单源迁移**；Icy 和 Maxroll互相校验，官方负责规则，天梯负责现实使用，Switch 实机负责平台终验。
5. **把 Switch 从页脚标签升级为验收维度**；尤其补齐火鸟气旋等主机独有构筑，并对所有 PC 来源展示平台风险。
6. **把准确性放在 UI 完整感之前**；宁可清楚显示“未验证/不推荐”，也不要继续展示看似完整但能让构筑失效的四套配置。
