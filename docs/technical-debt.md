# 技术债与还债计划

本文档记录当前项目中已经明确的技术债、影响范围和建议还债顺序。它不是“问题清单”那么悲观，更像施工图：哪些先拆、哪些可以等、每一步完成后应该怎样验收。

## 1. 债务总览

| 优先级 | 技术债 | 影响 | 当前状态 |
| --- | --- | --- | --- |
| P0 | `app/page.tsx` 单体过大 | 页面逻辑耦合、修改 BD/物品/设置容易互相影响 | 部分偿还：核心展示与设置已迁入 `components/` |
| P0 | `app/globals.css` 单体过大 | 暴雪风格、纸娃娃、物品库样式互相污染 | 部分偿还：`.guide-*` 旧层已删除，待按域拆 CSS 文件 |
| P0 | 路由由 `usePathname()` 手工分派 | 动态路由参数、404、元数据和测试都绕开了 App Router 的优势 | 先还 |
| P1 | 物品库全量 JSON 运行时加载 | 首屏和详情页都承担 2353 条物品记录成本 | 已偿还：索引、分类、详情三层拆包 |
| P0 | BD 场景配置与可替换项模型不完整 | 切换后可能只有文案变化，且无法表达真实装备/技能/巅峰策略 | 处理中：1 套完整样板、2 套部分实装、48 套待校对 |
| P1 | 官方物品结构化字段和兼容扁平字段并存 | 数据模型重复，后续消费者可能读错字段 | 已偿还：Schema V3 删除旧字段 |
| P1 | 抓取器缺少 HTML 夹具测试 | 暴雪官网 DOM 变化时可能静默丢字段 | 已偿还：五类离线夹具测试 |
| P2 | 赛季、平台、补丁规则分散 | 第 40 赛季或主机/PC 差异切换会变成全局搜索替换 | 已偿还：`season-config.ts` |
| P2 | 静态素材索引不统一 | 装备、技能、宝石图标映射依赖命名和少量手写映射 | 已偿还核心路径：`assets.ts` + 工厂统一入口 |
| P2 | 客户端设置只存在 `localStorage` | 换设备不会同步，设置结构升级需要兼容 | 部分偿还：v2 迁移和标签同步；跨设备需账号/D1 |
| P3 | D1/Drizzle 预留但未启用 | 当前没有坏处，但会让新开发者误判已有数据库能力 | 有持久化需求时再处理 |

## 2. P0：拆分单体页面文件

现状：

- `app/page.tsx` 约 2700 行，包含全站设置、首页、BD 列表、BD 详情、物品系统、剧情和开荒。
- `app/globals.css` 约 4800 行，包含全站布局、暗黑风格、纸娃娃、物品详情、列表、随从和资料页样式。

风险：

- 改一个局部 UI 时需要在大文件中定位，回归面很大。
- BD 详情和物品详情共享不少视觉类名，后续继续复刻暴雪样式时容易互相踩。
- 测试只能粗粒度校验构建产物，不容易针对组件做小范围验证。

还债方式：

1. 建立 `app/components/` 和 `app/features/` 目录。
2. 先把纯展示组件拆出，不改行为，例如 `BlizzardItemIcon`、`OfficialPropertyList`、`OfficialSetBlock`。
3. 再拆业务域：`build-detail`、`build-list`、`library`、`season-start`、`story`、`settings`。
4. CSS 按同样业务域拆成模块文件，最终由 `globals.css` 只负责全局变量、字体、背景和公共 reset。
5. 每拆一批跑一次 `npm test`，避免把大重构堆成一次不可回滚的改动。

验收标准：

- `app/page.tsx` 降到 300 行以内，只保留首页组合或临时兼容层。
- 任一业务组件文件不超过约 500 行。
- 纸娃娃、物品库和剧情/开荒样式不再共用高风险选择器。

## 3. P0：让 App Router 真正接管路由

现状：

- `app/builds/page.tsx`、`app/builds/[id]/page.tsx` 等路由入口都重新导出 `app/page.tsx`。
- 页面内部通过 `usePathname()` 判断当前路径。

风险：

- 动态参数没有类型化入口，`/builds/:id`、`/library/:category/:id` 的错误处理集中在一个客户端组件里。
- 页面元数据、标题和将来的静态生成不容易按路由配置。
- 新增路由时容易忘记在手工分派器中加分支。

还债方式：

1. 保留共享数据和组件，先把 `BuildAtlas` 放到 `app/builds/page.tsx`。
2. 把 `UnifiedBuildDetail` 放到 `app/builds/[id]/page.tsx`，从 `params.id` 读取构筑。
3. 物品目录、分类、详情按同样方式迁出。
4. 给找不到的 BD、分类、物品接入 `notFound()`。
5. 最后让 `app/page.tsx` 只负责首页跳转或默认展示。

验收标准：

- 业务路由不再依赖 `usePathname()` 判断页面类型。
- 动态详情页能独立生成标题和描述。
- 测试继续覆盖 `/builds`、`/builds/tragoul-nova`、`/library/pants/blackthornes-jousting-mail-unique_pants_013_x1` 等关键路径。

## 4. P1：物品库运行时拆包

状态：已完成。运行时使用 `asset-index.json`、`by-category/<category>.json` 和 `detail/<id>.json`，页面不再请求全量 `items.json`。

现状：

- 物品页面加载完整 `public/d3/library/items.json`。
- BD 详情为了匹配装备原特效，也可能需要读取全量物品记录。

风险：

- 2353 条记录会随着字段结构化继续变大。
- 用户进入单个物品详情时仍付出全库解析成本。
- 后续若补齐更多技能、怪物、任务、传奇威能，单 JSON 会越来越重。

还债方式：

1. 抓取器生成 `items/index.json`，只包含 ID、名称、分类、品质、等级、图片和筛选字段。
2. 按分类生成 `items/by-category/<category>.json`。
3. 按详情生成 `items/detail/<id>.json`，保留完整属性、套装清单和原特效。
4. BD 详情生成一份 `items/by-guide/<buildId>.json` 或 `items/powers-index.json`，只加载当前构筑会用到的官方记录。
5. 页面用小索引渲染列表，进入详情再加载完整记录。

验收标准：

- `/library` 不加载完整 `items.json`。
- `/library/:category` 只加载当前分类列表。
- `/builds/:id` 只加载当前 BD 关联物品记录。
- 测试增加“关键页面 HTML 中不引用全量 items.json”的断言。

## 5. P0：重建 BD 场景配置模型并逐套校对

状态：处理中。`completeBuildGuide()` 已停止自动替换未经校对的装备，但四份通用 profile 仍不能代表真实场景已经完成。完整实施路线见 [BD 内容与界面重构路线](./bd-content-and-ui-roadmap.md)。

现状：

- 塔格奥死亡新星有完整的 `resolveGear`、`resolvePowers`、`resolveRows`、`resolveRotation`，但仍缺新的巅峰和替换策略字段。
- 跑马天拳和上帝僧只有局部显式配置，不能覆盖全部用途与巅峰情况。
- 其余 48 套构筑大量依赖工厂默认逻辑，当前会明确显示共享配置提示。

风险：

- 用户切换冲层/速刷、低/高巅峰时，部分 BD 可能只有说明变化，没有装备、威能、宝石或手法变化。
- 后续补内容时不容易看出某套 BD 是否已经完成四种配置。

还债方式：

1. 用真实玩法场景替代固定 `push/speed`，每套 BD 自己声明适用内容。
2. 每个适用场景解析为完整装备、技能、被动、威能、宝石、随从、词缀和手法配置。
3. 增加固定/条件替换/自由槽位策略，以及替换条件、收益、代价和互斥关系。
4. 增加 800 点前、低巅峰、高巅峰的完整加点指导。
5. 工厂函数只负责结构性默认值，不再隐式制造“看似有差异”的内容。
6. 测试遍历 51 套 BD，断言适用场景存在真实 diff 或明确的无差异原因。
7. 按路线图逐套校对并独立提交，不通过同一套模板一次性填满。

验收标准：

- 切换任意 BD 的适用场景时，页面能展示由完整配置计算出的真实差异。
- 数据层能直接回答“什么必须固定、什么时候替换、换成什么、收益和代价是什么”。
- 每套 BD 都有可执行的巅峰加点指导和来源校对记录。

## 6. P1：收敛物品兼容字段

状态：已完成。Schema V3 和页面消费者均不再使用 `effects`、`setBonuses`。

现状：

- `items.json` 仍保留 `effects` 和 `setBonuses`。
- 新 UI 已使用 `properties` 和 `set`，但 BD 原特效查找仍存在兼容读取。

风险：

- 同一条数据有两种真相，后续修解析器时可能只修结构化字段，忘记更新扁平投影。
- JSON 体积变大。

还债方式：

1. 搜索所有 `effects`、`setBonuses` 消费者。
2. 为 BD 原特效新增专门选择器，例如 `getOfficialLegendaryText(record)`、`getOfficialSetBonusLines(record)`。
3. 所有 UI 只读取结构化字段。
4. 抓取器先保留生成兼容字段但测试不再依赖它们。
5. 确认没有消费者后删除兼容字段并升级 manifest/schema。

验收标准：

- 页面代码不再直接读取 `record.effects` 或 `record.setBonuses`。
- `items.json` schema 文档只保留结构化字段。

## 7. P1：给抓取器补夹具测试

状态：已完成。`tests/fixtures/diablo-items/` 覆盖传奇、套装、设计图、choice 和追随者/工匠。

现状：

- 当前测试覆盖生成后的 JSON 结果。
- 缺少固定 HTML 输入到解析器输出的契约测试。

风险：

- 官网 DOM 改动、繁中字段变化或嵌套结构变化时，抓取器可能生成字段缺失的数据。
- 只靠全量结果数量很难定位是哪一类 DOM 变了。

还债方式：

1. 从 `.cache/d3-items` 中挑 5 类样本，脱敏或裁剪后放入 `tests/fixtures/diablo-items/`：
   - 普通传奇
   - 套装装备
   - 套装设计图
   - 带多层 choice 的装备
   - 追随者或工匠物品
2. 把解析函数从脚本中导出为可测试模块。
3. 增加 Node Test Runner 用例，断言主要/次要/套装/等级/图标来源。

验收标准：

- 修改解析器时不需要联网即可验证复杂物品结构。
- 抓取器失败能定位到具体 HTML 样本。

## 8. P2：赛季与平台配置中心

状态：已完成。组件中的赛季号、补丁、平台和魔方槽说明统一引用 `app/data/season-config.ts`；BD 数据用 `seasonId` 标识版本。

附带完成：

- `app/data/assets.ts` 统一物品、技能、纸娃娃和职业图资源根路径。
- 网站设置升级为 v2 schema，自动迁移 v1，并通过 `storage` 事件同步同浏览器标签页。
- 真正跨设备同步需要稳定用户身份和 D1 数据表；当前私人本地站没有账号体系，暂不伪造匿名云同步。

现状：

- 第 39 赛季、第四魔方槽、NS/PC 基准说明散落在页面和数据中。

风险：

- 赛季切换时容易漏改页面文案、数据和测试。
- 主机版差异如果后续补充，无法按平台开关控制。

还债方式：

1. 新增 `app/data/season-config.ts`。
2. 集中保存赛季号、补丁、平台、规则开关、开荒礼包、主题说明。
3. 页面和测试统一引用配置。
4. 支持 `seasonId` 作为资料版本字段，为未来保留旧赛季攻略打基础。

验收标准：

- 搜索“第39赛季”只在配置、文档和历史说明中出现。
- 修改赛季号不需要改组件源码。

## 9. 建议还债路线

第一轮，稳定结构：

1. 拆 `BlizzardItemIcon`、物品详情组件和纸娃娃组件。
2. 拆 App Router 路由入口。
3. 把 `app/page.tsx` 降到可维护规模。

第二轮，稳定数据：

1. 补抓取器夹具测试。
2. 拆分物品 JSON。
3. 删除扁平兼容字段。

第三轮，稳定内容生产：

1. 升级 BD variant override 模型。
2. 给 51 套 BD 补完整差异验收。
3. 建立赛季配置中心。

第四轮，增强能力：

1. 需要收藏、个人配置云同步或后台编辑时再启用 D1。
2. 把资料库扩展到技能、宝石、任务和传奇威能的完整详情页。

## 10. 提交前还债检查

每还一项债，至少检查：

- 是否降低了文件尺寸或状态耦合，而不是只是移动代码。
- 是否保留了现有暴雪风格的纸娃娃、物品框和 tooltip 行为。
- 是否有回归测试保护关键路径。
- 是否更新了 `docs/architecture.md`、`docs/data-model.md` 或本文件。
- 是否能通过 `npm test`。
